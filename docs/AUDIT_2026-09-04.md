## What the project contains

Filesystem enumeration found 274 Lua files under `bots`, 128 `BotLib/hero_*.lua` files, 21 top-level mode files, and 23 TypeScript implementation files under `typescript/bots` (excluding declarations). The 128 BotLib files include Lone Druid's bear, so they represent 127 heroes plus that companion. Every internal name in the TypeScript hero enum has a matching BotLib file, and vice versa. File presence does not establish complete behavior coverage.

The only file under `asset` is `images/steam-profile-screenshot.jpg`. The gameplay assets in scope are primarily names, builds, weights, coordinates, and generated scripts; this clone does not contain the game's model/texture/animation archive. No visual-asset corruption was established.

## API capabilities and boundaries

Ordinary bot scripting and server VScript are different execution contexts. A server order enum does not make its corresponding server function available to a lobby bot. Preserve the separation already visible in the FretBots loading paths and test capabilities in each supported installation mode.

The bot API supports observing visible units, last-seen information, projectiles, ability behavior/target flags, cooldowns, cast points, damage estimates, team desires, and queued actions. These are enough to support richer local prediction and team planning. Visibility is a hard design constraint: `CanBeSeen()` means the querying team can see the unit, and many unit properties are invalid otherwise. [Bot API reference](https://docs.moddota.com/lua_bots/).

Build a thin compatibility layer that validates handles and capability availability, distinguishes player IDs from team indices, distinguishes seconds from timestamps, and records rejected actions. Keep knowledge about unseen enemies as timestamped estimates with uncertainty. Before trusting shared Lua tables for cross-bot coordination, verify the lifetime and visibility of that state across bot contexts in the intended installation.

## Concrete findings

Priorities indicate suggested repair order. The logical defects below are visible in source; actual match impact has not been measured. Line numbers refer to the audited commit.

### 1. P1: player ID used where a team-member index is required

`typescript/bots/FunLib/utils.ts:1244` iterates values from `GetTeamPlayers(bot.GetTeam())`, then calls `GetTeamMember(playerdId)`. The generated call is at `bots/FunLib/utils.lua:1697`. The local API reference correctly specifies a one-based team-member index at `docs/BOT_API_REFERENCE.md:209`.

`IsTeamPushingSecondTierOrHighGround()` therefore can inspect the wrong member or nil. For player IDs 5–9, calls 6–9 are outside the team-index domain. Its result gates Roshan participation and other decisions. Fix by pairing the correct one-based team index with its player ID; check alive status and position for the same member.

Verification: mock teams with IDs 0–4 and 5–9 and place exactly one qualifying group near the enemy base. Both sides must produce the same result. Repeat in-game because team ordering is an engine contract.

### 2. P1: nearby-hero filtering checks the observer instead of the candidate

`bots/FunLib/jmz_func.lua:2533` uses `not bot:HasModifier('modifier_arc_warden_tempest_double')` inside a loop over `hero`.

When the observer is a Tempest Double, every candidate is discarded. When the observer is an ordinary hero, that expression never excludes a candidate Double. Compare the candidate-based check in `GetEnemiesNearLoc()` at line 509. Use the candidate for the intended exclusion, then separately decide whether clones should be excluded from hero counts but included in combat-threat estimates.

Verification: ordinary observer and Double observer, each querying a real hero and a Double. Validate both list membership and downstream threat counting. Runtime call-path prevalence remains unmeasured.

### 3. P2: mixed unit lists repeat the first creep

`bots/FunLib/jmz_func.lua:2579` inserts `creepList[1]` on every loop iteration in `GetAroundBotUnitList()`.

With one hero and three creeps, the result is `[hero, creep1, creep1, creep1]`, omitting creeps 2 and 3. Consumers include Bounty Hunter's Shuriken selection (`BotLib/hero_bounty_hunter.lua:324`) and Rubick's Bounty Hunter helper (`FunLib/rubick_hero/bounty_hunter.lua:88`). This loses bounce candidates. Use the loop index and avoid mutating an input list if that list may later be cached/shared.

Verification: mixed hero/creep fixture with distinct handles; assert every input candidate appears exactly once. Exercise bounce selection with only the second creep in a useful position.

### 4. P2: target-lock callers bypass their own lock

`bots/mode_team_roam_generic.lua:53` defines `SetStickyTarget()` with a 1.2-second lock. Both help branches call it, then unconditionally overwrite `targetUnit` at lines 114 and 124.

If the lock rejects a new target, `bot:SetTarget()` retains the old target while `Think()` can attack the new `targetUnit`. This defeats stability and makes ability targeting disagree with attack targeting. Return the accepted target from the helper or make it the sole writer; invalidate the lock when its target dies, becomes invalid, or an emergency warrants switching.

Verification: offer two different valid targets inside the lock window; internal and engine target must agree. Then test expiration and invalid-target escape.

### 5. P2: Roshan health scale mismatch

`bots/mode_roshan_generic.lua:77` computes health/maxHealth; line 79 remaps it from `100` to `0`.

For any health ratio below 0.5, the interpolation fraction is above 0.995, almost the absolute-desire endpoint. The intended graduation collapses. Keep the existing health gate if desired, but use a ratio-scale range such as 1 to 0, or explicitly choose 0.5 to 0 as a design decision.

Verification: sample 49%, 25%, and 1% health; document the intended desire curve and verify that higher-priority emergency behavior can still intervene.

### 6. P2: false results never hit the utility cache

`typescript/bots/FunLib/utils.ts:449` tests cached values by truthiness; generated Lua at `bots/FunLib/utils.lua:1066` returns nil for a stored false. Zero is truthy in Lua, so the confirmed generated-Lua defect is specifically false values, not zero values.

`IsTeamPushingSecondTierOrHighGround()` actively stores false, causing repeated team scans during the common negative case. Use an explicit missing-value check. `CleanupCachedVars()` is also an unconditional return; measure distinct key growth before calling that a memory leak. A separate `global_cache` implementation exists, so consolidate contracts before expanding caching.

Verification: store false, retrieve it before expiry, and verify expiry afterwards. Count underlying world-query calls before and after. Do not simply re-enable the commented nearby-hero cache: its source records prior crashes and its old keying ignores query mode.

### 7. P2: API documentation reverses visibility semantics

`docs/BOT_API_REFERENCE.md:1165` describes `CanBeSeen()` as visibility to the enemy team. The accessible bot reference describes visibility to the querying team, with allied bots always visible. This is a documentation defect, not proof that every existing call is wrong. [ModDota bot reference](https://docs.moddota.com/lua_bots/).

Correct the row and add a friendly/enemy example. Validate other semantic claims before using this document to generate more code.

### 8. P2: patch guide contradicts itself about Bloodstone

`docs/PATCH_UPDATE_GUIDE.md:306` says the active changed rather than disappeared. Lines 360 and 486 say it was removed. `ability_item_usage_generic.lua:1698` currently implements an active handler. The guide could cause a future maintainer to disable it again.

Resolve against patch-matched item data and the installed game, then retain one consistent instruction. This audit does not adjudicate Bloodstone's current gameplay behavior from conflicting prose.

### 9. P3: ping assembly repeatedly extends its expiry

`bots/mode_assemble_generic.lua:29` resets expiry to now plus five seconds on every evaluation while the same ping remains recent for eight seconds. A bot that remains outside the arrival radius can therefore continue almost thirteen seconds after that ping, rather than five.

This is a mismatch with the local duration comment; desired behavior is a product decision. Track a processed ping identity/time and establish expiry once if five seconds is intended. Test repeated evaluations, new pings, arrival, and danger interruption.

## Data coverage and maintenance gaps

**Neutral pools differ intentionally in two places.** After excluding enhancements, Buff has 11/9/8/9/10 items across tiers, and FretBots has 12/9/9/9/10. Buff explicitly comments out Forager's Kit (line 40) and Psychic Headband (line 80), citing complex actives; FretBots includes them at lines 40 and 82. Both appear in the fetched [neutral catalog](https://raw.githubusercontent.com/dotabuff/d2vpkr/master/dota/scripts/npc/neutral_items.txt). These are documented exclusions, not accidental missing names. Preserve an explicit allowlist with reasons and check active-use support before restoring them.

**Largo has no identifier in the matchup database.** Hero selection loads `FretBots/matchups_data.lua` and guards missing rows at `hero_selection.lua:608`. Largo thus lacks this statistical adjustment rather than necessarily crashing. The bear's absence is expected for a non-draftable companion. Add provenance, sample counts, and a deliberate unknown-matchup fallback before adding synthetic scores.

**Spell-list omissions need consumer-aware review.** Literal hero keys for Lone Druid, Morphling, and Rubick are absent from `spell_list.lua`; this file is used by Morphling, so those omissions may be intentional. A string-presence scan alone cannot establish a missing hero implementation. Likewise, `bots/ts_libs/matchups.lua` is empty, but the active draft code loads the separate FretBots dataset; the empty file is not evidence that drafting has no data.

**Patch and generated-source provenance are incomplete.** Review 7.41b–e changes against actual abilities, items, talents, and map behavior. Dynamic API reads cover some numeric changes; hardcoded thresholds, formulas, special-value keys, slot assumptions, and range multipliers still require review. The guide's broad claim that number-only changes require no code can miss these cases.

**Verification infrastructure is missing from the normal workflow.** `package.json` has build/release/data-generation scripts but no test script; no dedicated test suite was found by filename search. The `dev` script runs TSTL watch without the release path-rewrite step used by `build:lua`, so parity needs checking. The post-processor logs read/write errors without setting a failing exit status. A build can therefore appear successful despite a failed rewrite. Dependencies are absent in this checkout; no build was run.

## How to make the bots more coordinated and dangerous

These are proposed experiments grounded in the observed architecture, not measured performance improvements.

| Experiment | Integration | Observable success criterion |
|---|---|---|
| Team objective commitments | Extend push/defend/Roshan modes with objective ID, rally point, required participants, readiness, expiry, and abort rules. Prototype shared-state visibility first. | Fewer solo arrivals/deaths, shorter arrival spread, higher objective conversion after won fights. |
| Disable and burst scheduling | Add short-lived target reservations to shared tactical helpers: predicted impact time, disable end, planned damage, interrupt urgency. Account for cast point, projectile travel, immunity, and invalidation. | Less overlapping stun time and overkill; more successful chain disables, without delaying emergency interrupts. |
| Threat estimates under fog | Extend last-seen helpers with age, reachable region, observed mobility, and visible teleport information. Increase uncertainty rather than assume unseen enemies disappeared. | Fewer deaths during unsafe pushes and Roshan attempts, without permanent passivity. |
| Role-aware focus fire | Score exposed supports, channelers, save heroes, damage threats, and reachable targets; include allied follow-up and disengage cost. | Better kill conversion and lower pursuit deaths at equal resources. |
| Farm and support assignments | Reserve camps/waves for short intervals; price travel, danger, role priority, and missed lane XP. Coordinate ward, smoke, and aura purchases. | Less duplicated travel/farming, better core income, fewer redundant team items. |
| Stable mode arbitration | Apply hysteresis and minimum commitment windows with explicit emergency overrides; keep action target and ability target consistent. | Fewer mode switches, cancelled attacks/casts, and movement oscillations. |
| Bounded perception snapshots | Profile existing `global_cache` and uncached helpers; use slower strategic snapshots and fresher tactical checks, always revalidating handles. | Lower p95/p99 think time and API-call count without more stale-target actions. |

Start with reliability and target stability, then objective commitments and disable scheduling. Those experiments act on many heroes through shared code. Treat drafting statistics as advisory, because human-match advantages do not necessarily transfer to the subset of mechanics these bots execute well.

## Implementation and validation sequence

1. Record the installed Dota build/patch, game mode, installation method, FretBots settings, and baseline commit. Preserve the baseline so comparisons are repeatable.
2. Add focused Lua 5.1 mock regressions for findings 1–6 and the chosen ping contract. Repair pure Lua directly; repair TS-owned behavior in TS and regenerate it.
3. Add a data audit that parses active definitions rather than comments. Check hero-to-script coverage, names and special-value keys against a pinned catalog, neutral tiers and exclusions, role-build item expansion, and ability action/target compatibility. Maintain explicit exceptions for companions, virtual item bundles, copied spells, and alternate abilities.
4. Add syntax checks for shipped Lua, isolated build/post-process validation, generated-file drift detection, and nonzero failure exits. Pin one package-lock workflow for CI rather than allowing uncontrolled dependency resolution.
5. Add bounded diagnostic counters: mode transitions, target changes, accepted/rejected casts, invalid handles, API queries, purchase stalls, idle durations, and decision times. Log reason codes and sampled events, not every frame. Keep diagnostics out of player chat.
6. Run controlled in-game scenarios: both teams; ordinary/companion units; talent and skill upgrades; dispels and immunity; interrupt chains; Roshan pressure; fog retreats; neutral distribution; and purchase progression. Test standard bots and FretBots separately.
7. Compare baseline and candidate across a fixed lineup suite with side swaps and recorded randomness/settings. Report win rates with uncertainty alongside last hits, GPM/XPM, avoidable deaths, objective conversion, stun overlap, and frame cost. A small winning streak is not evidence of improved intelligence.
8. Implement one coordination experiment at a time behind a configuration flag. Keep resource bonuses identical during comparisons so decision quality is measurable.
